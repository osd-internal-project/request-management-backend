01ขอบเขตของงานชุดนี้

งานชุดนี้คือรากฐานที่ทุกโมดูลธุรกิจ (CRM, Sales, Pre-Sales, Pricing, Legal, PM, Engineer, Delivery, Service, HR, MACOM) ต้องเรียกใช้ร่วมกัน ตามหลักการของข้อเสนอโครงการที่ให้เริ่มระยะที่ 1 ที่ Platform Request ก่อน เพราะถ้าสร้างโมดูลธุรกิจก่อนแล้วค่อยทำระบบคำขอทีหลัง จะต้องกลับไปแก้ทุกโมดูลที่ทำไปแล้ว

อยู่ในขอบเขต INไม่อยู่ในขอบเขต OUT
  • SSO ผ่าน Keycloak เชื่อม LDAP ของบริษัท (D-07)
  • ซิงก์ผู้ใช้ ผังองค์กร และสายบังคับบัญชาจาก LDAP (D-08)
  • โครงสร้างบทบาทและสิทธิ์ (RBAC) พร้อมหน้าจอผู้ดูแล
  • Data Scope ระดับแถวข้อมูล + การปกปิดฟิลด์อ่อนไหว
  • รองรับหลายบริษัทตั้งแต่ต้น (D-11)
  • Platform Request ครบ 10 ฟีเจอร์ตามข้อเสนอ
  • Approval Engine ครบ 6 ฟีเจอร์ตามข้อเสนอ (D-31)
  • SLA-นับเวลาขั้นต่ำ + แจ้งเตือนในระบบ/อีเมลขั้นต่ำ + Audit log
  • เปิดใช้จริง 2 ประเภทคำขอนำร่อง: ขอส่วนลด และ ส่งต่อโอกาสการขาย (เดินบนเครื่องยนต์เดียวกับอีก 28 ประเภทที่จะทยอยตั้งค่าภายหลัง)
  • โมดูลธุรกิจทั้ง 11 โมดูล (แยก sprint ถัดไป)
  • เครื่องยนต์ SLA กลางฉบับเต็ม (ปฏิทินเวลาทำการหลายบริษัท, กะ, รายงานตามกำหนดเข้า Data Mart) — sprint นี้ทำเฉพาะนาฬิกาขั้นต่ำ
  • ศูนย์แจ้งเตือนกลางฉบับเต็ม (กติกาจากเหตุการณ์, เทมเพลตหลายบริษัท, แชทองค์กร)
  • ระบบ PDPA กลาง (sprint นี้เตรียมเฉพาะจุดเสียบ masking)
  • ระบบลงนามอิเล็กทรอนิกส์
  • Odoo Connector, Reserve-phone, D-Callcenter, LLM Gateway
  • Data Lake / Metabase
  • ผู้ช่วย AI ทุกตัว
เหตุผลที่เลือกคำขอนำร่อง 2 ประเภทนี้: ข้อเสนอโครงการกำหนดผลวัดเมื่อจบระยะที่ 1 ว่า "คำขอส่วนลดและการส่งต่อ Lead เดินในระบบทั้งหมด เลิกใช้อีเมลสำหรับสองเรื่องนี้" — คำขอส่วนลดเป็นตัวทดสอบ Approval Engine ตามวงเงินที่ดีที่สุด ส่วนการส่งต่อโอกาสการขายเป็นตัวทดสอบเส้นทางข้ามทีมที่เบาที่สุด · หมายเหตุ: ใน sprint นี้ยังไม่มีโมดูล Pricing การแสดง margin ในคำขอส่วนลดจึงเป็นช่องกรอกตัวเลขพร้อมไฟล์แนบ ยังไม่ใช่การคำนวณอัตโนมัติ

02ข้อตกลงที่ผูกพันการออกแบบ

ข้อสรุปจากรอบทบทวนกับเจ้าของกระบวนการ (หัวข้อ 07 ของข้อเสนอ) ที่มีผลตรงต่องานชุดนี้ ทีมพัฒนาต้องยึดตามนี้ ห้ามออกแบบขัดแย้งโดยไม่ผ่าน PO:

รหัสข้อตกลงผลต่อการออกแบบ
D-07ระบบล็อกอินกลางใช้ Keycloak เชื่อมกับ LDAP ของบริษัท · ยืนยันเพิ่ม (PO): LDAP ใช้ยืนยันตัวตน (login) เท่านั้น — role กำหนดที่ Keycloak · มี Keycloak instance ใช้งานอยู่แล้วไม่สร้างระบบจัดการรหัสผ่านเอง ทุกบริการตรวจ token จาก Keycloak เท่านั้น · role อ่านจาก claims ใน token (Keycloak roles/groups)
D-08ระดับอำนาจอนุมัติกำหนดในระบบ · ปรับจากข้อเสนอเดิม (PO): เมื่อ LDAP ใช้ล็อกอินอย่างเดียว ผังทีมและสายบังคับบัญชาจึงดูแลในระบบนี้ผ่านหน้าจอผู้ดูแล ไม่ซิงก์จาก LDAPระบบเป็นแหล่งความจริงของ "ใครสังกัดทีมไหน ใครคือหัวหน้า" (ใช้กับ Data Scope ระดับ team และการเร่งงาน) · ตารางอำนาจอนุมัติเป็นข้อมูลของระบบนี้ แก้ผ่านหน้าจอผู้ดูแล
D-09กำหนดเวลา (SLA) ของคำขอเป็นค่าตั้งค่า ใส่ตัวเลขจริงตอนเตรียมเปิดใช้งานSLA เก็บเป็น config ต่อประเภทคำขอต่อบริษัท ห้าม hardcode
D-11ต้องรองรับหลายบริษัทและหลายสกุลเงินตั้งแต่ต้นทุก entity หลักมี company_id · วงเงินอนุมัติระบุสกุลเงิน
D-02 / D-19เลขที่เอกสารใช้ปี ค.ศ. + เดือน รีเซ็ตลำดับทุกเดือน · รหัสบริษัทในเลขเอกสารตั้งค่าได้รายประเภทเอกสารเครื่องออกเลขคำขอเป็นบริการกลาง รูปแบบตั้งค่าได้ เช่น OSD-DSC-202608-0042
D-16การอนุมัติภายในใช้การกดอนุมัติในระบบพร้อมร่องรอยตรวจสอบ ไม่ต้องลงนามเป็นเอกสารไม่ต้องรอระบบลงนามอิเล็กทรอนิกส์ — Approval Engine เริ่มได้ใน sprint นี้
D-18อำนาจอนุมัติหลายบริษัท แต่ละบริษัทใช้ระเบียบของตัวเองตารางอำนาจอนุมัติแยกชุดตามบริษัท ไม่ใช่ชุดเดียวทั้งกลุ่ม
D-31แยกงานอนุมัติออกจาก Platform Request เป็นบริการกลางApproval Engine เป็นบริการแยก มี API ของตัวเอง ให้โมดูลอื่นเรียกใช้ได้โดยไม่ต้องสร้างคำขอ
D-34SLA และการแจ้งเตือนแยกเป็นบริการกลาง ตั้งค่าจากหน้าจอผู้ดูแลSprint นี้สร้างโครง (interface) ของทั้งสองบริการ แต่ implement เฉพาะความสามารถขั้นต่ำในหัวข้อ 09

03สถาปัตยกรรมภาพรวม

องค์ประกอบของงานชุดนี้และเส้นทางการเรียกใช้:

Browser / Mobile │ OIDC (Authorization Code + PKCE) ▼ Keycloak (instance ที่มีอยู่แล้ว) ──── LDAP (ยืนยันตัวตนเท่านั้น) │ access token (JWT: ตัวตน + roles จาก Keycloak) ▼ API Gateway / Backend ├─ Identity & Org Service ← โปรไฟล์ผู้ใช้ · ผังทีม/หัวหน้า (ดูแลในระบบ) · ทะเบียนบริษัท ├─ Policy Service (RBAC+Scope) ← ทุก endpoint ต้องผ่านจุดนี้จุดเดียว ├─ Request Service ← Platform Request + เครื่องออกเลข + state machine ├─ Approval Service ← ตารางอำนาจ · เส้นทางอนุมัติ · มอบอำนาจ ├─ SLA Timer (ขั้นต่ำ) ← due date · หยุด/เดินนาฬิกา · เร่งงาน ├─ Notification (ขั้นต่ำ) ← in-app + อีเมล └─ Audit Log Service ← ทุกการเปลี่ยนสถานะ/สิทธิ์/การเข้าถึงข้อมูลอ่อนไหว
  • หลักการข้อเดียวที่สำคัญที่สุด: การตรวจสิทธิ์ (role + scope) ทำที่ชั้น backend ผ่าน Policy Service จุดเดียว — การซ่อนปุ่ม/เมนูที่ frontend เป็นเรื่องความสะดวกผู้ใช้ ไม่ใช่การควบคุมสิทธิ์
  • ทุกบริการเป็นเจ้าของข้อมูลตัวเอง เรียกข้ามผ่าน API ภายใน ไม่อ่านตารางข้ามบริการ
  • Frontend เดียว (SPA) เมนูและการมองเห็นประกอบจาก permission ที่ backend ส่งให้หลังล็อกอิน

04AUTH — ระบบล็อกอินกลาง (SSO)

เป้าหมาย: พนักงานทุกคนเข้าระบบด้วยบัญชีองค์กรเดิมผ่าน Keycloak โดยระบบรู้ตัวตน สังกัด บริษัท และบทบาท ตั้งแต่วินาทีที่ล็อกอิน

รหัสข้อกำหนดเกณฑ์ตรวจรับ
AUTH-01ล็อกอินผ่าน Keycloak (instance ที่มีอยู่แล้ว) ด้วย OIDC Authorization Code + PKCE · Keycloak federate ไปที่ LDAP เพื่อยืนยันตัวตนเท่านั้น ระบบนี้ไม่เก็บและไม่เห็นรหัสผ่าน · role ทั้งหมดกำหนดที่ Keycloak ไม่อ่านกลุ่มจาก LDAPล็อกอินด้วยบัญชี LDAP สำเร็จ · รหัสผ่านผิดถูกปฏิเสธที่ Keycloak · ไม่มีรหัสผ่านวิ่งผ่าน backend ของระบบ · token มี roles จาก Keycloak ครบ
AUTH-02Session: access token อายุสั้น (แนะนำ 15 นาที) + refresh token · idle timeout และอายุ session สูงสุดตั้งค่าได้ที่ Keycloak realmtoken หมดอายุแล้วเรียก API ไม่ได้ (401) · refresh ต่ออายุได้โดยผู้ใช้ไม่รู้สึกสะดุด
AUTH-03Logout ล้าง session ทั้งฝั่งแอปและ Keycloak (single logout) · บัญชีที่ถูกปิดใน LDAP/Keycloak ต้องใช้งานต่อไม่ได้ภายในไม่เกินอายุ access tokenหลัง logout เปิด API ด้วย token เดิมไม่ได้ · ปิดบัญชีทดสอบแล้วสิ้นสิทธิ์ภายใน 15 นาที
AUTH-04สร้างโปรไฟล์ผู้ใช้อัตโนมัติเมื่อล็อกอินครั้งแรก (JIT provisioning) จาก claims ใน token: ชื่อ อีเมล username · ผังทีม สังกัด และหัวหน้า ดูแลในระบบนี้ผ่านหน้าจอผู้ดูแล (LDAP ใช้ล็อกอินอย่างเดียว) — ผู้ใช้ใหม่ที่ยังไม่ถูกจัดสังกัดขึ้นรายการ "รอจัดสังกัด" ให้ผู้ดูแลเห็นผู้ใช้ใหม่ใน LDAP ล็อกอินได้ทันทีโดยไม่ต้องสร้างบัญชีมือ · ผู้ดูแลย้ายสังกัด/เปลี่ยนหัวหน้าจากหน้าจอ แล้ว Data Scope และการเร่งงานเปลี่ยนตามทันที
AUTH-05ผู้ใช้หนึ่งคนสังกัดได้หลายบริษัท (D-11) มีบริษัทหลักหนึ่งแห่ง · ระบบจำบริษัทที่ทำงานอยู่ (active company) และให้สลับได้โดยไม่ต้องล็อกอินใหม่ผู้ใช้สองบริษัทสลับบริษัทแล้วข้อมูลและสิทธิ์เปลี่ยนตามทันที · ผู้ใช้บริษัทเดียวไม่เห็นตัวเลือกสลับ
AUTH-06Service account (client credentials) สำหรับระบบที่เรียก API อัตโนมัติ เช่น การสร้างคำขอจากเหตุการณ์ (REQ-10) แยก client ต่อระบบ ระบุ scope ที่เรียกได้service account เรียกได้เฉพาะ endpoint ใน scope ตน · เรียกนอก scope ได้ 403
AUTH-07บันทึกเหตุการณ์เข้าระบบ: ล็อกอินสำเร็จ/ล้มเหลว เวลา ช่องทาง IP — อ่านได้จากหน้าจอผู้ดูแลเหตุการณ์ล็อกอินทดสอบปรากฏใน log ครบทุกรายการ
สิ่งที่ต้องได้จากทีม Infra ก่อนเริ่ม: สิทธิ์เข้าจัดการ realm/client บน Keycloak instance ที่มีอยู่ (สร้าง client, กำหนด roles), ค่าเชื่อมต่อ SMTP ของ mail server องค์กร และบัญชีทดสอบครอบคลุมทุกบทบาท — ดูหัวข้อ 15

05ROLE — สิทธิ์ตามบทบาท (RBAC)

เป้าหมาย: อำนาจการทำงาน (ทำอะไรได้) แยกออกจากขอบเขตข้อมูล (เห็นอะไรได้ — หัวข้อ 06) · บทบาทตั้งค่าได้จากหน้าจอผู้ดูแล ไม่ฝังในโค้ด

5.1 โครงสร้าง

  • Permission = โมดูล + การกระทำ เช่น request.create, request.cancel.any, approval.matrix.manage, admin.role.manage
  • Role = ชุดของ permission ตั้งชื่อได้ เช่น "พนักงานขาย", "ผู้จัดการฝ่ายขาย" · หนึ่งผู้ใช้มีได้หลาย role ต่อบริษัท (สิทธิ์รวมแบบ union)
  • การผูก role: role หลักกำหนดที่ Keycloak (มากับ token เป็น claims) — ระบบ map "Keycloak role → role ในระบบ" ด้วยตาราง mapping ที่ตั้งค่าได้ และผู้ดูแลผูกมือเพิ่ม/ถอนในระบบได้ ทุกครั้งลง audit log
  • ระดับอำนาจอนุมัติไม่ใช่ role — เป็นข้อมูลของ Approval Engine (ตาม D-08) role เพียงกำหนดว่าใครเปิดหน้าจออนุมัติได้

5.2 บทบาทตั้งต้น (seed)

บทบาทคำอธิบายสิทธิ์หลักใน sprint นี้
พนักงาน (ทุกคน)บทบาทพื้นฐานที่ทุกผู้ใช้ได้อัตโนมัติยื่นคำขอ, ดู/ยกเลิกคำขอของตัวเอง, รับแจ้งเตือน
หัวหน้าทีมผู้บังคับบัญชาระดับต้น (อ่านจากผังทีมที่ดูแลในระบบ)เห็นคำขอของลูกทีม, อนุมัติชั้นแรก (ตรวจสิทธิ์การยื่นคำขอ)
ผู้จัดการฝ่ายผู้บังคับบัญชาระดับฝ่ายเห็นคำขอทั้งฝ่าย, อนุมัติตามตารางอำนาจ, ดูรายงานคอขวดของฝ่าย
ผู้บริหารผู้อำนวยการ / C-levelเห็นข้ามฝ่ายในบริษัทตน, อนุมัติวงเงินสูง, ดูรายงานทั้งหมด
ทีมผู้รับคำขอ (Receiver)ผู้ปฏิบัติงานของทีมปลายทาง เช่น ทีม Pricing ที่รับคำขอส่วนลดเห็นคิวคำขอของทีมตน, ตีกลับพร้อมเหตุผล, ปิดงาน, เห็นฟิลด์อ่อนไหวของประเภทที่ทีมตนรับ
ผู้ดูแลระบบ (Admin)ทีมที่ดูแลการตั้งค่าจัดการ role/mapping, ประเภทคำขอ, ตารางอำนาจอนุมัติ, SLA, ดู audit log · ไม่มีสิทธิ์อนุมัติแทนใคร
ผู้ตรวจสอบ (Auditor)ตรวจสอบภายในอ่านทุกอย่างรวม audit log — อ่านอย่างเดียว แก้อะไรไม่ได้

5.3 ข้อกำหนด

รหัสข้อกำหนดเกณฑ์ตรวจรับ
ROLE-01ทุก API endpoint ประกาศ permission ที่ต้องมี และตรวจที่ backend ทุกครั้ง · ไม่มี endpoint ที่ "เปิดไว้ก่อน"เรียก endpoint โดยไม่มี permission ได้ 403 ทุกกรณี · มี test ครอบคลุมทุก endpoint
ROLE-02หน้าจอผู้ดูแล: สร้าง/แก้/ปิด role, กำหนด permission, ผูก/ถอน role กับผู้ใช้ · role ที่มีผู้ใช้ผูกอยู่ลบไม่ได้ (ปิดใช้งานได้)ตั้ง role ใหม่และผูกผู้ใช้ได้จากหน้าจอโดยไม่แตะโค้ด · ผลมีผลทันทีในการเรียก API ครั้งถัดไป
ROLE-03Mapping อัตโนมัติจาก Keycloak role (claims ใน token) → role ในระบบ ตั้งค่าได้ต่อบริษัท · ประเมินใหม่ทุกครั้งที่ล็อกอิน/refresh token — ถอน role ที่ Keycloak แล้วสิทธิ์ในระบบหายตามเปลี่ยน role ใน Keycloak แล้วสิทธิ์ในระบบปรับตามภายในอายุ access token พร้อมบันทึกใน audit log
ROLE-04role ผูกกับบริษัท: ผู้ใช้หลายบริษัทมี role คนละชุดต่อบริษัทได้ สิทธิ์คิดตาม active company เท่านั้นผู้ใช้เป็นผู้จัดการบริษัท A / พนักงานบริษัท B — เมื่อ active ที่ B ใช้สิทธิ์ผู้จัดการไม่ได้
ROLE-05ทุกการเปลี่ยนสิทธิ์ (role ใหม่, ผูก/ถอน, mapping) ลง audit log: ใคร ทำอะไร กับใคร เมื่อไร ค่าเดิม→ค่าใหม่สุ่มตรวจการเปลี่ยนสิทธิ์ 5 รายการ ตอบได้ครบทุกคำถาม
ROLE-06หลังล็อกอิน frontend ได้รายการ permission + scope ของผู้ใช้หนึ่งครั้ง ใช้ประกอบเมนู/ปุ่ม · แคชฝั่ง client ไม่เกินอายุ access tokenผู้ใช้ไม่มีสิทธิ์อนุมัติ ไม่เห็นเมนูอนุมัติ และเรียกตรงก็ได้ 403

06SCOPE — ขอบเขตการเห็นข้อมูล (Data Scope)

เป้าหมาย: คนสองคนที่มีสิทธิ์ทำงานเหมือนกัน อาจเห็นข้อมูลไม่เท่ากัน — พนักงานเห็นของตัวเอง หัวหน้าเห็นของทีม ตามหลัก "พนักงานเห็นของตัวเอง หัวหน้าเห็นของทีม" ในข้อเสนอ และเป็นชุดสิทธิ์เดียวกับที่ Metabase และผู้ช่วย AI ส่วนบุคคลจะใช้ในระยะถัดไป

6.1 ระดับขอบเขต

ระดับความหมายตัวอย่าง
ownเฉพาะรายการที่ตนเป็นเจ้าของ ผู้ยื่น หรือผู้เกี่ยวข้องโดยตรง (ผู้อนุมัติในสาย, ผู้รับมอบหมาย)พนักงานขายเห็นเฉพาะคำขอที่ตนยื่น
teamรายการของทุกคนใต้สายบังคับบัญชาตน (อ่านจากผังทีมที่ดูแลในระบบ, รวมหลายชั้น)หัวหน้าทีมเห็นคำขอของลูกทีมทุกคน
departmentรายการของทั้งฝ่ายผู้จัดการฝ่ายขายเห็นคำขอทั้งฝ่ายขาย
companyทุกรายการในบริษัทที่ activeผู้บริหารเห็นทั้งบริษัท
allข้ามบริษัท (สงวนไว้สำหรับผู้บริหารกลุ่มและ Auditor)ตรวจสอบภายในเห็นทุกบริษัท

6.2 ข้อกำหนด

รหัสข้อกำหนดเกณฑ์ตรวจรับ
SCOPE-01ขอบเขตกำหนดเป็นคู่ (role, ชนิดข้อมูล) → ระดับ scope ตั้งค่าได้จากหน้าจอผู้ดูแล · ค่าตั้งต้นตามตาราง 5.2ปรับ scope ของ role จาก own เป็น team จากหน้าจอ แล้วผลลัพธ์ query เปลี่ยนโดยไม่ deploy ใหม่
SCOPE-02บังคับที่ชั้น query กลาง (query filter / policy layer จุดเดียว) — ทุกรายการ list, การเปิดดูรายตัว, ตัวเลขสรุปบนแดชบอร์ด ใช้ตัวกรองเดียวกัน · ห้ามให้แต่ละหน้าจอเขียนเงื่อนไขเองเข้าถึงรายการนอก scope ตรง ๆ ทาง URL/API ได้ 404 หรือ 403 · ตัวเลขสรุปกับรายการที่เห็นตรงกันเสมอ
SCOPE-03เส้นแบ่งบริษัทเด็ดขาด: ทุก query ผูกกับ active company เว้นแต่ scope all · ไม่มีกรณี "ลืมกรองบริษัท"ผู้ใช้บริษัท A ค้น/เดา id ของบริษัท B ไม่พบข้อมูลใด ๆ · มี test อัตโนมัติกันการถดถอย
SCOPE-04การปกปิดฟิลด์อ่อนไหว (field-level masking): ประกาศรายการฟิลด์อ่อนไหวต่อชนิดข้อมูล (เช่น margin, วงเงิน, อัตราต้นทุนบุคลากร) พร้อม permission ที่เปิดเห็นได้ · ผู้ไม่มีสิทธิ์เห็นค่าถูกปกปิด ทั้งใน API response ไม่ใช่แค่หน้าจอผู้ใช้ไม่มีสิทธิ์เห็น margin ได้ response ที่ไม่มีฟิลด์นั้น (หรือ masked) · ผู้มีสิทธิ์เห็นค่าจริง
SCOPE-05การเปิดดูข้อมูลอ่อนไหวลง audit log: ใครเปิดดูฟิลด์อ่อนไหวของรายการใด เมื่อไร (รองรับข้อกำหนด PDPA "บันทึกว่าใครเปิดดูข้อมูลของใคร" ที่จะต่อยอดในระยะถัดไป)เปิดดูรายการที่มีฟิลด์อ่อนไหวแล้วมี log เกิดขึ้น
SCOPE-06ผู้อยู่ในเส้นทางอนุมัติเห็นคำขอนั้นได้เสมอแม้อยู่นอก scope ปกติ (สิทธิ์ตามความเกี่ยวข้องรายรายการ) และสิ้นสุดเมื่องานจบ ยกเว้นประวัติที่ตนกระทำผู้อนุมัติข้ามฝ่ายเปิดคำขอที่รออนุมัติตนได้ · คำขอที่ไม่เกี่ยวกับตนยังมองไม่เห็นตาม scope
ข้อควรระวังเชิงเทคนิค: scope team อิงสายบังคับบัญชาหลายชั้น — ให้เก็บ closure ของผังองค์กร (ตาราง ancestor–descendant) ที่คำนวณใหม่ทุกครั้งที่ผู้ดูแลแก้ผังทีม แทนการ traverse ตอน query เพื่อให้ list เร็วและเงื่อนไข SQL ตรงไปตรงมา

07REQ — โมดูลคำขอ (Platform Request)

เป้าหมาย: คำขอข้ามทีมทุกประเภทเดินบนเครื่องยนต์เดียว ทุกใบมีเลขอ้างอิง ผู้รับผิดชอบ เอกสารบังคับ กำหนดเวลา และร่องรอยตรวจสอบ · เครื่องยนต์ต้องรองรับคำขอทั้ง 30 ประเภทได้ด้วย "การตั้งค่า" — sprint นี้เปิดใช้จริง 2 ประเภทนำร่อง

7.2 ข้อกำหนด

REQ-01ประเภทคำขอเป็นข้อมูลตั้งค่า: ชื่อ, ทีมผู้รับ, ฟอร์มข้อมูล (custom fields ต่อประเภท), เอกสารบังคับ, เส้นทางอนุมัติ (อ้าง Approval Engine), SLA, บริษัทที่เปิดใช้ · เพิ่ม/แก้จากหน้าจอผู้ดูแลโดยไม่ deployผู้ดูแลสร้างประเภทคำขอที่ 3 ได้เองจากหน้าจอ และยื่น–อนุมัติ–ปิดได้จริงโดยทีมพัฒนาไม่แตะโค้ด
REQ-02ออกเลขคำขอทันทีที่ยื่น ตามรูปแบบ D-02: ยืนยันแล้ว (PO) ว่าใช้ prefix ชื่อบริษัท — รูปแบบมาตรฐาน {PREFIX บริษัท}-{ประเภท}-{YYYYMM}-{ลำดับ} เช่น OSD-DSC-202608-0042 ลำดับรีเซ็ตทุกเดือน · prefix ต่อบริษัทตั้งค่าในทะเบียนบริษัท · เลขไม่ซ้ำแม้ยื่นพร้อมกัน (กัน race condition)ยื่นขนาน 50 ใบ เลขไม่ซ้ำ ไม่กระโดดผิดรูปแบบ · ขึ้นเดือนใหม่ลำดับเริ่ม 1 · คำขอของสองบริษัทได้ prefix ต่างกันถูกต้อง
REQ-03บังคับเอกสารแนบและฟิลด์บังคับตั้งแต่หน้าจอยื่น: ยื่นไม่ได้จนกว่าจะครบตามที่ประเภทคำขอกำหนด พร้อมบอกว่าขาดอะไรยื่นคำขอส่วนลดโดยไม่แนบไฟล์บังคับ ระบบไม่รับและแจ้งรายการที่ขาด
REQ-04ตีกลับพร้อมระบุสิ่งที่ขาดเป็นรายการ (เลือกจากรายการมาตรฐานของประเภทนั้น + ข้อความเพิ่มเติม) ไม่ใช่ข้อความอิสระอย่างเดียว เพื่อวัดสาเหตุตีกลับได้ตีกลับต้องเลือกเหตุผลอย่างน้อย 1 ข้อ · รายงานสรุปเหตุผลตีกลับต่อประเภทคำขอดูได้
REQ-05ยกเลิกคำขอ: ได้เฉพาะผู้ยื่นหรือผู้มีสิทธิ์เหนือกว่า ต้องระบุเหตุผล คำขอยังค้นเจอในระบบ (ไม่ลบ)ผู้อื่นยกเลิกคำขอของคนอื่นไม่ได้ · คำขอที่ยกเลิกยังเปิดดูได้พร้อมเหตุผล
REQ-06สร้างคำขอจากบริบท: โครงสร้างคำขอรองรับการอ้างอิง entity ต้นทาง (ref_type, ref_id เช่น ดีล, ลูกค้า) และดึงข้อมูลบริบทมาเติมฟอร์มอัตโนมัติ · sprint นี้ยังไม่มีโมดูลธุรกิจ ให้ทำโครงสร้างและทดสอบผ่าน APIสร้างคำขอผ่าน API พร้อม ref แล้วหน้าคำขอแสดงลิงก์บริบทได้
REQ-07บันทึกทุกการเปลี่ยนสถานะ: เวลา ผู้กระทำ ค่าก่อน–หลัง อ่านได้จากหน้าไทม์ไลน์ของคำขอ · แก้ไขย้อนหลังไม่ได้ (append-only)ตอบคำถาม "ใครอนุมัติเมื่อไร ด้วยข้อมูลชุดใด" ได้จากหน้าจอเดียว
REQ-08หน้าจอรวมงานค้าง: แท็บ "คำขอของฉัน" (ที่ยื่น/เกี่ยวข้อง ทุกสถานะ) และ "รออนุมัติของฉัน" ข้ามทุกประเภทคำขอ พร้อมตัวกรอง สถานะ ประเภท วันครบกำหนด และป้ายบอกใกล้/เกินกำหนดผู้อนุมัติเห็นรายการรออนุมัติทั้งหมดในหน้าเดียว เรียงตามความเร่ง · จำนวนตรงกับข้อมูลจริง
REQ-09รายงานคอขวด: เวลาที่ใช้จริงต่อขั้น แยกตามประเภทคำขอ ผู้อนุมัติ และช่วงเวลา · นับเฉพาะเวลาที่นาฬิกาเดิน (หักช่วงตีกลับ)รายงานระบุได้ว่าคำขอค้างที่ขั้นใด/ที่ใครนานที่สุดในเดือนที่เลือก
REQ-10API สร้างคำขออัตโนมัติ: endpoint ให้ระบบภายใน (ผ่าน service account) สร้างคำขอเมื่อเกิดเงื่อนไข เช่น สัญญาใกล้หมดอายุ · sprint นี้ส่งมอบ API + เอกสาร ยังไม่มีตัวจุดชนวนservice account สร้างคำขอผ่าน API ได้ และคำขอระบุแหล่งที่มาว่าสร้างโดยระบบ
REQ-11คำขอนำร่อง 2 ประเภท ตั้งค่าพร้อมใช้: ขอส่วนลด (Sales → Pricing, เส้นทางมาตรฐาน 8.1: หัวหน้าทีม → CFO เมื่อเกิน T1 → CEO เมื่อเกิน T2, ฟิลด์: ดีล/ลูกค้า, มูลค่า, % ส่วนลด, margin โดยประมาณ + ไฟล์แนบ) และ ส่งต่อโอกาสการขาย (CRM → Sales, อนุมัติชั้นเดียวโดยหัวหน้าทีม, SLA 4 ชม.)ทั้งสอง flow เดินจบ ยื่น→อนุมัติ→ปิด ได้จริงบน UAT โดยผู้ใช้จากทีมขาย

08APV — เครื่องยนต์อนุมัติกลาง (Approval Engine)

เป้าหมาย: อำนาจอนุมัติทั้งบริษัทอยู่ในตารางเดียว ทุกโมดูลเรียกใช้ร่วมกัน — บริการนี้แยกจาก Platform Request (D-31) และต้องเรียกใช้ได้จากงานที่ไม่ใช่คำขอ เช่น อนุมัติราคา/สัญญาในระยะถัดไป

8.1 เส้นทางอนุมัติมาตรฐาน (ยืนยันโดย PO)

ทุกคำขอเดินเส้นทาง 3 ชั้นตามนี้ โดยจำนวนชั้นที่ต้องผ่านจริงขึ้นกับวงเงิน:

ชั้นที่ 1 หัวหน้าทีมของผู้ยื่น ← อนุมัติเสมอทุกใบ: ตรวจว่าผู้ยื่นมีสิทธิ์ยื่นคำขอนี้และข้อมูลสมเหตุสมผล ชั้นที่ 2 CFO ← เพิ่มเมื่อวงเงินเกินเพดานระดับที่ 1 (T1) ชั้นที่ 3 CEO ← เพิ่มเมื่อวงเงินเกินเพดานระดับที่ 2 (T2) วงเงิน ≤ T1 : หัวหน้าทีม T1 < วงเงิน ≤ T2 : หัวหน้าทีม → CFO วงเงิน > T2 : หัวหน้าทีม → CFO → CEO
  • ค่า T1 และ T2 เป็นค่าตั้งค่าในตารางอำนาจอนุมัติ แยกตามบริษัทและประเภทงาน (D-18) — ตัวเลขจริงยังไม่ยืนยัน (คำถามเปิดข้อ 3) ระหว่างพัฒนาให้ใช้ค่าสมมติ
  • "หัวหน้าทีมของผู้ยื่น" อ่านจากผังทีมที่ดูแลในระบบ (AUTH-04) — คำขอที่ผู้ยื่นยังไม่มีหัวหน้าในผังต้องยื่นไม่ได้ พร้อมข้อความแจ้งให้ติดต่อผู้ดูแล
  • คำขอที่ไม่มีมิติวงเงิน (เช่น ส่งต่อโอกาสการขาย) ใช้เฉพาะชั้นที่ 1 หรือผู้อนุมัติที่ประเภทคำขอกำหนด

8.2 ข้อกำหนด

รหัสข้อกำหนดเกณฑ์ตรวจรับ
APV-01ตารางอำนาจอนุมัติกลาง: กำหนดเพดานวงเงิน T1/T2 และผู้อนุมัติแต่ละชั้นตาม (บริษัท, ประเภทงาน, ช่วงวงเงิน+สกุลเงิน) · ค่าตั้งต้นตามเส้นทางมาตรฐาน 8.1 (หัวหน้าทีม → CFO → CEO) · แยกชุดตามบริษัท (D-18) · แก้จากหน้าจอผู้ดูแล มีเวอร์ชันและวันมีผลตั้ง T1/T2 ของคำขอส่วนลดจากหน้าจอ แล้วคำขอจริงเดินตาม: ต่ำกว่า T1 จบที่หัวหน้าทีม เกิน T2 เดินครบสามชั้น · บริษัท A/B ใช้เพดานต่างกันได้
APV-02เลือกเส้นทางอนุมัติอัตโนมัติ: ระบบคำนวณชั้นผู้อนุมัติจากประเภทงานและวงเงิน ณ ขณะยื่น ตามเส้นทาง 8.1 · ผู้ยื่นเลือกผู้อนุมัติเองไม่ได้ · ผู้อนุมัติต้องไม่ใช่ผู้ยื่น — หัวหน้าทีมยื่นเอง ชั้นที่ 1 เลื่อนขึ้นเป็นหัวหน้าของตน · CFO/CEO ยื่นเอง ชั้นของตนถูกข้ามเปลี่ยนวงเงินในคำขอแล้วจำนวนชั้นเปลี่ยนตามกติกา · หัวหน้าทีมยื่นเองแล้วเส้นทางเริ่มที่หัวหน้าของตน
APV-03มอบอำนาจชั่วคราว: ผู้อนุมัติตั้งผู้ทำแทนพร้อมช่วงเวลา · งานที่ค้างและงานใหม่ในช่วงนั้นไปที่ผู้ทำแทน · บันทึกเสมอว่า "ใครอนุมัติแทนใคร" · ห้ามมอบต่อเป็นทอดที่สองตั้งมอบอำนาจ 7 วัน งานวิ่งไปผู้ทำแทน หมดช่วงแล้วกลับสู่ปกติอัตโนมัติ · ประวัติแสดงชื่อทั้งคู่
APV-04อนุมัติเป็นชุด: รวมคำขอที่อ้างอิงบริบทเดียวกัน (เช่น ดีลเดียวกัน) ให้อนุมัติพร้อมกันได้ในครั้งเดียว โดยผลการอนุมัติยังบันทึกแยกรายใบเลือก 3 คำขอของดีลเดียวกัน กดอนุมัติครั้งเดียว ทุกใบได้ผลและ log ของตัวเอง
APV-05อนุมัติผูกกับเวอร์ชันข้อมูล: การอนุมัติบันทึก snapshot/hash ของข้อมูลที่อนุมัติ · แก้ไขสาระสำคัญหลังอนุมัติทำให้การอนุมัติเป็นโมฆะ ระบบบังคับขอใหม่แก้มูลค่าในคำขอหลังอนุมัติ → สถานะอนุมัติถูกยกเลิกอัตโนมัติและต้องเข้าเส้นทางอนุมัติใหม่
APV-06ประวัติการใช้อำนาจ: รายงานใครอนุมัติอะไร เมื่อไร วงเงินเท่าไร รวมการอนุมัติแทน · export ได้ · อ่านได้เฉพาะบทบาทที่มีสิทธิ์Auditor ดึงรายงานการอนุมัติย้อนหลัง 1 เดือนได้ครบทุกรายการ
APV-07API แบบบริการกลาง: โมดูลใดก็ได้ส่ง "เรื่องขออนุมัติ" (subject type + payload + บริบทวงเงิน) เข้ามาโดยไม่ต้องเป็นคำขอ Platform Request · ตอบกลับผ่าน callback/event เมื่อผลออกทดสอบส่งเรื่องอนุมัติจาก mock service เดินครบวงจรได้โดยไม่สร้าง request record
การกดอนุมัติ (ตาม D-16): ใช้การกดยืนยันในระบบพร้อมร่องรอยตรวจสอบ ไม่ต้องลงนามอิเล็กทรอนิกส์ · หน้าจออนุมัติต้องแสดงข้อมูลสำคัญครบ (ผู้ยื่น วงเงิน เหตุผล เอกสารแนบ margin ถ้ามี) ก่อนปุ่มอนุมัติ/ปฏิเสธ/ตีกลับ และการปฏิเสธบังคับระบุเหตุผลเสมอ

09SUP — บริการขั้นต่ำที่ต้องมีร่วม

เครื่องยนต์ SLA กลางและศูนย์แจ้งเตือนกลางฉบับเต็มเป็นงานระยะที่ 1 เช่นกัน แต่แยกคนละ sprint — sprint นี้ต้องมี "ขั้นต่ำ" เพียงพอให้คำขอและการอนุมัติทำงานได้จริง โดยออกแบบ interface ให้ถอดเปลี่ยนเป็นฉบับเต็มได้โดยไม่แก้ Request/Approval Service:

รหัสข้อกำหนดเกณฑ์ตรวจรับ
SUP-01นาฬิกา SLA ขั้นต่ำ: กำหนดเวลาต่อประเภทคำขอ (ชั่วโมง/วันทำการ ตั้งค่าได้ D-09) · เริ่มนับเมื่อยื่น หยุดเมื่อตีกลับ เดินต่อเมื่อยื่นใหม่ · ปฏิทินวันหยุดชุดเดียวต่อบริษัท (ยังไม่ทำกะ/หลายปฏิทิน)คำขอ SLA 4 ชม. ที่ถูกตีกลับ 1 วัน ครบกำหนดถูกเลื่อนตามเวลาที่หยุดจริง
SUP-02เร่งงานอัตโนมัติ: เกินกำหนดแล้วแจ้งผู้รับผิดชอบ + ผู้บังคับบัญชาหนึ่งระดับ (อ่านจากผังทีมที่ดูแลในระบบ) · บันทึกว่าเร่งไปเมื่อไรถึงใครปล่อยคำขอทดสอบเกินกำหนด มีการแจ้งครบสองระดับภายใน 15 นาทีหลังครบกำหนด
SUP-03แจ้งเตือนขั้นต่ำ: in-app + อีเมลผ่าน SMTP ของ mail server องค์กร (ยืนยันแล้ว) — ค่าเชื่อมต่อเก็บเป็น config ต่อสภาพแวดล้อม · เหตุการณ์: มีงานรออนุมัติ, ถูกตีกลับ, ผลอนุมัติออก, ใกล้ครบกำหนด (ตั้งค่าล่วงหน้าได้), เกินกำหนด · ทุกการส่งลง log (ส่งถึงใคร เมื่อไร ช่องทางใด)ทุกเหตุการณ์ในรายการมีแจ้งเตือนทั้งสองช่องทาง · log ตอบข้อโต้แย้ง "ไม่เคยได้รับแจ้ง" ได้
SUP-04Audit Log กลาง: บริการเดียวรับเหตุการณ์จากทุกบริการ (สิทธิ์, สถานะคำขอ, การอนุมัติ, การเข้าถึงข้อมูลอ่อนไหว, การตั้งค่าผู้ดูแล) · append-only · ค้นตามผู้กระทำ ชนิดเหตุการณ์ ช่วงเวลาเหตุการณ์จากทุกหมวดค้นเจอในที่เดียว · ไม่มี API แก้/ลบ log

10โครงสร้างข้อมูลหลัก

Entity หลักที่ต้องมี (ชื่อฟิลด์ให้ทีมออกแบบรายละเอียดเอง แต่ความสัมพันธ์และข้อบังคับต้องครบตามนี้):

Identity & Org

  • company — รหัส, ชื่อ, รหัสในเลขเอกสาร, สกุลเงินหลัก
  • user — ผูก LDAP id, บริษัทหลัก, สถานะ
  • user_company — สังกัดหลายบริษัท
  • org_unit — ทีม/ฝ่าย + หัวหน้า (ดูแลในระบบผ่านหน้าจอผู้ดูแล) + org_closure สำหรับ scope
  • role, permission, role_permission, user_role (ต่อบริษัท), keycloak_role_mapping
  • scope_rule — (role, ชนิดข้อมูล) → ระดับ scope
  • sensitive_field_rule — ชนิดข้อมูล, ฟิลด์, permission ที่เห็นได้

Request

  • request_type — ผู้รับ, ฟอร์ม (JSON schema), เอกสารบังคับ, SLA, เส้นทางอนุมัติอ้างอิง, บริษัทที่เปิดใช้, สถานะเปิด/ปิด
  • request — เลขที่, ประเภท, บริษัท, ผู้ยื่น, สถานะ, ข้อมูลฟอร์ม, ref_type/ref_id, วันครบกำหนด
  • request_attachment, request_return_reason
  • request_event — ไทม์ไลน์ append-only
  • doc_number_config + doc_number_counter (ต่อบริษัท/ประเภท/เดือน)

Approval

  • approval_matrix — บริษัท, ประเภทงาน, ช่วงวงเงิน, สกุลเงิน, ลำดับชั้น, เวอร์ชัน, วันมีผล
  • approval_case — subject type/id, snapshot hash, สถานะ
  • approval_step — ชั้น, ผู้อนุมัติที่คำนวณได้, ผลการพิจารณา, เวลา, อนุมัติแทนโดย

11ข้อกำหนด API (API Specification)

11.1 ข้อตกลงร่วมทุก endpoint

  • Base URL: /api/v1 · REST + JSON (UTF-8)
  • Authentication: header Authorization: Bearer <access_token> (JWT จาก Keycloak) ทุก endpoint — ไม่มีข้อยกเว้น
  • บริษัทที่ทำงานอยู่: header X-Company-Id ทุก request · backend ตรวจว่าผู้ใช้สังกัดบริษัทนั้นจริง มิฉะนั้น 403 COMPANY_FORBIDDEN
  • Pagination: query page (เริ่ม 1), page_size (default 20, max 100) · response ห่อรูปแบบเดียวกันเสมอ:
    { "data": [ ... ], "page": 1, "page_size": 20, "total": 137 }
  • Sort/Filter: sort=field หรือ sort=-field (desc) · filter เป็น query param ตรงชื่อฟิลด์
  • Error format เดียวทั้งระบบ:
    { "code": "REQ_DOC_MISSING", "message": "เอกสารบังคับยังไม่ครบ", "details": [ { "field": "attachments", "reason": "ต้องแนบใบเสนอราคาฉบับร่าง" } ] }
  • เวลา: ISO 8601 UTC (2026-08-24T07:30:00Z) · จำนวนเงิน: string ทศนิยม + currency แยกฟิลด์ เช่น {"amount":"150000.00","currency":"THB"}
  • Idempotency: ทุก POST ที่เปลี่ยนสถานะรองรับ header Idempotency-Key — ส่งซ้ำด้วย key เดิมได้ผลเดิม ไม่เกิดรายการซ้ำ (รองรับ NFR-03)

Statusใช้เมื่อ

13การแบ่ง Sprint และลำดับพัฒนา

Sprintส่งมอบผลที่ demo ได้เมื่อจบ
S1
รากฐานตัวตน		AUTH-01…07 · ROLE-01…06 · SCOPE-01…06 · SUP-04 (audit log) · โครง project, CI, สภาพแวดล้อม (NFR-07)ล็อกอินด้วยบัญชีองค์กร สลับบริษัท เห็นเมนูตามสิทธิ์ · ผู้ดูแลตั้ง role/scope จากหน้าจอ · ทุกการเปลี่ยนสิทธิ์ตรวจย้อนได้

14เกณฑ์ตรวจรับรวม (Definition of Done)

  • ทุกข้อกำหนดมี automated test อย่างน้อยหนึ่งรายการที่ผูกกับรหัส (AUTH-xx, ROLE-xx, …) และผ่านใน CI
  • ชุดทดสอบสิทธิ์ต้องมี negative case ครบ: ทุก endpoint ถูกทดสอบด้วยผู้ใช้ที่ "ไม่มีสิทธิ์" และ "ผิดบริษัท" อย่างน้อยหนึ่งกรณี
  • เอกสาร OpenAPI ตรงกับของจริง (generate จากโค้ด) และคู่มือหน้าจอผู้ดูแลฉบับย่อพร้อมใช้
  • ผ่าน UAT script ต่อไปนี้กับผู้ใช้จริงอย่างน้อย 3 คน (พนักงานขาย, ผู้จัดการ, ผู้ดูแลระบบ):
    1. พนักงานขายยื่นคำขอส่วนลดพร้อมไฟล์แนบ → หัวหน้าทีมได้รับแจ้งเตือน → อนุมัติจากมือถือ
    2. คำขอที่เอกสารไม่ครบถูกตีกลับพร้อมรายการ → แก้แล้วยื่นใหม่ → นาฬิกา SLA หักช่วงตีกลับถูกต้อง
    3. คำขอวงเงินเกิน T2 เดินครบสามชั้น (หัวหน้าทีม → CFO → CEO) → แก้ตัวเลขหลังชั้นแรกอนุมัติ → การอนุมัติเป็นโมฆะและเข้าเส้นทางใหม่
    4. CFO ลาพักร้อน ตั้งมอบอำนาจ → งานวิ่งถึงผู้ทำแทน → ประวัติระบุการอนุมัติแทน
    5. ผู้ใช้บริษัท A พยายามเปิดคำขอบริษัท B ทาง URL ตรง → ไม่พบข้อมูล
  • ผลทดสอบประสิทธิภาพตาม NFR-02 แนบท้ายรายงานปิด sprint
